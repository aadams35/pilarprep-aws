# Resource Names and Storage Migration

## Rollout Status

The interface cleanup is live at `https://pilarprep.app`, and the existing
CloudFront distribution has the console name `pilarprep-demo-web`.
Four private S3 destinations have been created and populated: `web-assets`,
`artifacts`, `meeting-evidence`, and `deployments`. The vector bucket is planned
but has not been created. Original buckets are still serving the application.

The storage cutover is pending operator approval because it changes the connected
Lambda permissions, malware-scanning configuration, and evidence index together.
The queue consumer is still running. No original bucket has been detached or deleted.
Use the read-only `status` phase to distinguish proposed names from live storage;
this document is not evidence that the migration has completed.

## Naming Convention

S3 names use `pilarprep-<environment>-<purpose>-<account>-<region>`.
The account and region suffixes make ownership clear and avoid global-name collisions.

| Resource | Purpose | Example suffix |
| --- | --- | --- |
| Frontend S3 | React assets served through CloudFront | `web-assets` |
| Artifact S3 | Job inputs, results, approved packets, JSON and DOCX | `artifacts` |
| Meeting S3 | Authorized uploads, transcripts and approved evidence | `meeting-evidence` |
| Deployment S3 | Packaged Lambda and AgentCore code | `deployments` |
| S3 Vectors | Embeddings for the approved-evidence Knowledge Base | `evidence-vectors` |
| CloudFront | Website and workspace API edge | `pilarprep-<environment>-web` |

CloudFront's `Name` tag is its console display name. Its distribution ID and AWS-assigned
hostname do not change. The existing custom domain, certificate, WAF association,
private origin access, and HTTPS policies remain in place.

The historical `pillarprep-*` stack names and function prefixes remain unchanged.
Changing those would replace unrelated resources and is not required to name storage
professionally.

## Configuration

- `infrastructure/bedrock.yaml`: `ArtifactBucketName`.
- `infrastructure/jobs-pipeline.yaml`: `MeetingEvidenceBucketName`,
  `EvidenceVectorBucketName`, and `KnowledgeBaseGeneration`.
- `infrastructure/frontend.yaml`: `FrontendBucketName` and `CloudFrontName`.
- Deployment scripts accept `PackagingBucket`; the frontend accepts `BucketName`.
- `scripts/resource-names.ps1` supplies consistent names for new deployments and
  preserves existing storage settings on subsequent deployments.

An empty optional name on an existing stack preserves its autogenerated bucket.
Do not set a new bucket parameter directly on a populated deployment:
S3 cannot rename a bucket in place, and a replacement begins empty.

## Existing-Deployment Migration

The opt-in `scripts/migrate_resource_names.py` utility is specific to the four
PilarPrep stacks. It requires the `PilarPrepHackathonDeployer` role, checks the
account, validates change sets, and refuses unexpected resource removals or
replacements. Install `requirements-dev.txt` first.

Start with a read-only inventory:

```powershell
python scripts/migrate_resource_names.py inventory --profile pillarprep-deployer --account-id YOUR_ACCOUNT_ID
```

Review the proposed names and schedule a quiet maintenance window. The staged phases are:

1. `prepare`: create private, encrypted destinations and copy current objects.
   Uploaded audio is deliberately excluded until the new scan protection is active.
2. `retain`: apply retention safeguards and naming parameters without moving data.
3. `pause`: verify the queue is idle and no nonterminal jobs remain, then pause only
   queue consumption. Submitted jobs can still wait in SQS.
4. `cutover-core`: point core consumers to the populated artifact bucket, retain the
   original, and import the replacement under the same logical resource ID.
5. `cutover-jobs`: move the meeting bucket, update artifact permissions, activate
   malware protection, and replace retained vector storage and its Knowledge Base.
6. `reindex`: ingest the copied approved evidence into the new vector index.
7. `cutover-agent`: update AgentCore's artifact, packaging and retrieval references;
   refresh the shared worker's SDK layer reference.
8. `rescan-audio`: reset verification for eligible, unexpired uploads and copy them
   without GuardDuty result tags. The new scan must verify each new object version.
9. `resume`: copy any final input changes and resume the shared worker.
10. `cutover-frontend`: switch the existing distribution to the populated web bucket
    and import that bucket into the frontend stack.

Run each phase explicitly, check its result, then continue:

```powershell
python scripts/migrate_resource_names.py prepare --apply --profile pillarprep-deployer --account-id YOUR_ACCOUNT_ID
python scripts/migrate_resource_names.py status --profile pillarprep-deployer --account-id YOUR_ACCOUNT_ID
```

Repeat the phase command for the reviewed phases above. Do not automatically
continue after a failure. The utility retains snapshots, copy manifests, and
pre-rescan metadata in ignored `work/resource-names/`. These files may contain
private object keys and must not be committed or shared.

After cutover, publish the current frontend and wait for its CloudFront invalidation.
Verify fresh-browser sign-in, generation, downloads, evidence retrieval, and an
authorized BlueMesa audio upload. Never reuse a successful scan from the old
bucket as proof that a new object version passed scanning.

## Retention and Rollback

- The original buckets, original object versions, vector index, and Knowledge Base
  are retained. Only current objects are copied into the active S3 buckets.
- Expired, blocked, failed-scan, or unowned audio is not activated in the new bucket.
  Existing lifecycle and access policies still apply to the originals.
- The utility does not delete original objects. It mirrors a source deletion only
  when the corresponding destination object was created by this migration and has
  not subsequently changed.
- The deployment-packaging bucket is managed by deployment scripts; data buckets
  remain managed by their existing CloudFormation stacks.
- An incomplete migration is not a reason to purge a bucket or remove public-access
  protections. Use the saved templates and object manifests to reconcile it.
- Restoring an old bucket requires restoring the relevant permissions, input/output
  references, retrieval configuration and scan identities together, followed by
  CloudFormation import. A bucket-name-only rollback is not sufficient.
- Remove retained resources only after an explicit, separately reviewed cleanup.
  Keeping both copies temporarily adds storage charges.

## Interface

The workspace no longer shows the synthetic-data badge or a demo MP3 download
button. Audio selection is still manual and still requires authentication,
recording authorization, and a successful GuardDuty scan. The fictional scenarios
and the underlying demo audio asset are retained.
